# AGENTS.md — Pi WSL Desktop

> **Обязательно для любого AI-разработчика, subagent и участника репозитория.**
> Сначала прочитай [PRODUCT.md](PRODUCT.md) и [SPECIFICATION.md](SPECIFICATION.md). Не опирайся на память о проекте вместо GitHub.

## 1. Роли и приоритеты

- **GitHub — источник истины**: задачи и решения в Issues, изменение кода через PR, состояние по коммитам и тестам.
- **Владелец проекта** утверждает merge и изменение границ продукта.
- **Pi / разработчик** работает крупными тематическими пакетами, применяет TDD и документирует результат.
- **Независимый ревьюер** оценивает diff, архитектуру, тесты и риски; не объявляет непроверенное выполненным.
- При конфликте реализация должна следовать принятому **PRODUCT.md**, затем **SPECIFICATION.md**, затем утверждённым решениям Issues/PR; противоречия фиксируются и выносятся на согласование.

## 2. Рабочее дерево и безопасность

- Единственное допустимое место разработки на рабочем ПК:
  - Windows: `F:\_hermes\CODE\pi-wsl-desktop`
  - WSL: `/mnt/f/_hermes/CODE/pi-wsl-desktop`
- **Не создавать дополнительные копии репозитория разработки** на `C:` / `E:`. Системные каталоги npm и приложения этому ограничению не противоречат.
- **Не модифицировать VoiceForge, ChatWake, Hermes** и иные репозитории в рамках этой работы.
- Не удалять и не перезаписывать без согласия существующие Pi-сессии, модели, `~/.pi/agent/`, ключи, настройки и расширения.
- Не запускать `wsl --unregister`, переустановку дистрибутива, `wsl --shutdown` при активной работе, массовое удаление или миграцию пользовательских данных.
- Запрещено коммитить токены, `auth.json`, `.env`, секреты MCP, реальную историю сессий и дампы пользовательских каталогов.

## 3. Архитектурные инварианты

1. **Не переписывать Pi**. Использовать установленный в WSL Pi через CLI RPC или поддерживаемый SDK.
2. **Нет второй конфигурации Pi на Windows** и нет копий его истории.
3. Сессии идентифицируются исходным путём/ID, проектом, WSL-дистрибутивом и активным агентным каталогом.
4. Исполнение Skills, Extensions и MCP происходит **в WSL**, управление ими — через документированные Pi CLI/API или ограниченные WSL-адаптеры.
5. Поддерживать глобальные/проектные scopes, пользовательские каталоги, модель доверия Pi и безопасные read-only сценарии.
6. Никакого HTTP-listener на внешних интерфейсах по умолчанию. Если нужен локальный транспорт — защищённый и ограниченный.
7. Никаких бесконечных блокирующих запусков shell или неконтролируемых повторных операций записи.
8. В M0–M2 предпочитать **простую статическую модульность**. Запуск непроверенного стороннего JS внутри Electron не требуется.

## 4. Работа со Skills (обязательно для Pi и subagents)

- **В начале каждой новой сессии и перед каждым макропакетом** сверить доступный каталог Skills для текущего Pi: пользовательские, проектные, пакетные и из окружения. Делать компактный inventory `имя / описание / источник / применимость`: Pi и так обнаруживает метаданные навыков, поэтому не печатать весь каталог и не читать все `SKILL.md` подряд.
- **Использовать все доступные и применимые к задаче Skills**: не ограничиваться заранее фиксированным списком. Например, при наличии и применимости — планирование, `test-driven-development`, `systematic-debugging`, `verification-before-completion`, `code-review`, `writing-plans` и другие. Это **примеры**, а не утверждение об установленном наборе или разрешение пропускать новые Skills.
- **По запросу задачи** прочитать полный `SKILL.md` каждого реально применимого Skill **перед его первым использованием** и соблюдать все инструкции. Если уже прочитан в этой сессии и не изменился, повторно не перечитывать; читать вложенные reference-файлы только по конкретному требованию Skill. Новые/изменённые Skills всегда перечитывать. Это оптимизация повторного контекста, **не** разрешение пропускать применимые Skills. Если нужны дополнительные разрешения или инструменты — соблюдать безопасность.
- Нерелевантные Skills не запускать ради формальности. Противоречащие проектному контракту или небезопасные инструкции Skill не исполнять; явно указать причину исключения.
- Передавая задачу subagent, передать требования к подходящим Skills и проверить их применение по фактическим данным отчёта.
- **В каждом PR и перед review:** отчёт `Skills discovered / loaded / applied / unavailable / skipped (with reason)` с точными именами; нельзя заявлять `used` для Skill, который не был загружен и применён.

## 5. Разработка крупными этапами

- Работа начинается с открытого Issue и завершённого описания ограничений, зависимостей и acceptance criteria.
- **[ROADMAP.md](ROADMAP.md) — обязательный реестр прогресса.** Каждая завершённая задача/подзадача должна быть отражена в чекбоксах ROADMAP со ссылкой на доказательство в GitHub. PR, меняющий реализацию, одновременно обновляет соответствующий пункт ROADMAP; без синхронизации ROADMAP PR не принимается. `[x]` разрешается только после подтверждённой приёмки, не по самоотчёту разработчика. Если итоговая приёмка зависит от merge, выполнить финальную отметку следующим PR. Историю принятых задач не удалять.
- Один **связный большой PR на этап** или несколько обоснованных пакетов. Не дробить исправления на десятки PR по 10–50 строк.
- До реализации проверить установленный Pi: версию, фактические возможности RPC/SDK, структуру сессий и ресурсные команды. Документация upstream не заменяет проверку текущей версии.
- **TDD**: сначала воспроизводимый тест/контракт, затем минимальное исправление, потом полный регрессионный тест.
- Предпочитать устранение продуктового блокера, а не самостоятельное развитие инфраструктуры.
- Успешные unit tests не заменяют реальный Windows + WSL smoke; недоступные проверки маркировать как `NOT RUN`.
- **Тестовый стек:** Vitest (unit, contracts, integration), React Testing Library (компоненты), Zod (валидация протокола), Playwright + Electron (E2E), TypeScript и ESLint (статические проверки). Настоящий Windows 11 + Ubuntu WSL2 + существующий Pi — отдельная обязательная приёмка этапов. См. [SPECIFICATION.md §8](SPECIFICATION.md#8-тестирование-и-критерии-приёмки).
- Соблюдать `Red → Green → Refactor`; лог с красной проверкой до изменения и зелёной после. Контрактные фикстуры, отсутствие мутации файлов и негативные сценарии обязательны.

### Публичный GitHub и бесплатный CI

- Репозиторий **PUBLIC**: весь коммит, diff, Actions log и загружаемые артефакты потенциально общедоступны. Не выводить сведения о локальной системе, Pi-сессии, MCP токены, `.env` или историю в отчёты.
- GitHub Actions: **только стандартные `ubuntu-latest` / `windows-latest` runners**. Не использовать larger runners, платные сервисы или артефакты без согласования.
- Для сторонних PR использовать `pull_request` и `permissions: contents: read`, без `pull_request_target`, `workflow_run` для непроверенного кода, доступных секретов, PR self-hosted runner или привилегированных токенов.
- С M0 [PR #4](https://github.com/triagmas/pi-wsl-desktop/pull/4) имеются реальные сборка, Product CI и тесты. **Repository Contract** по-прежнему проверяет документы/политику, но не заменяет Vitest/E2E/Windows+WSL.
- Не заменять реальные тесты фиктивным PASS и не пропускать release/security gates ради снижения стоимости.

## 5.1. Экономия токенов и выбор усилия (обязательный рабочий протокол)

> Полная процедура, примеры и измерения: [docs/TOKEN_EFFICIENCY.md](docs/TOKEN_EFFICIENCY.md). **Цель — снизить общий расход на принятое изменение, а не число токенов в одной реплике.** Дефекты, повторные прогоны и потеря контекста тоже расходуют токены.

- **Уровень рассуждения по риску задачи**, при поддержке выбранной моделью: `off/minimal/low` — read-only GitHub/status, ссылки, документация, тривиальные механические действия; `medium` — стандартная реализация и TDD; `high` — архитектурные решения, безопасность, конкуренция, протокол, неочевидные регрессии и независимое принятие PR. Начинать с минимального **адекватного** уровня, повышать при двух содержательных неудачных попытках или обнаруженном риске; после сложной части возвращать низкий.
- **Не считать текст `AGENTS.md` переключателем модели.** Фактические `/model`, `/thinking`, `defaultThinkingLevel`, `modelThinkingLevels` принадлежат работающему Pi и его настройкам. Проверять совместимость с установленной версией и согласовывать изменения текущей конфигурации с владельцем. Не включать неизвестный/платный провайдер автоматически; не утверждать, что `off` или `low` всегда лучше/дешевле.
- **Компактный контекст:** при старте прочитать компактные статусы `git status`, текущий Issue/PR, относящиеся к задаче разделы документов; полный контракт/Skill перечитывать при изменении или в новом требующем этого контексте. Проверка актуальности GitHub обязательна. Не вводить отдельную память как замену GitHub.
- **Ограниченные выводы инструментов:** сначала `git diff --stat`, список нужных файлов, точечный поиск, затем диапазон строк; не присылать LLM полный CI-лог, бинарные файлы, `node_modules`, lockfile или тысячи строк успешных тестов без причины. На ошибке сохранять полный исходный лог локально, передавать релевантный фрагмент + статус/команду; не скрывать ошибки и не публиковать секреты.
- **Тестирование по двум уровням:** во время Red→Green гонять сфокусированные тесты; перед финальным отчётом/PR-review **обязательно** полный typecheck/lint/build/Vitest/E2E/соответствующий native smoke. После изменения, затрагивающего безопасность/контракт, запустить релевантные проверки заново. Не запускать полный набор в цикле без изменений и объяснения.
- **Субагенты:** применять только для узких независимых задач с чётким входом (SHA + файлы + критерии) и коротким результатом; не передавать историю всех чатов. Параллельный дубляж одного и того же ревью не считается экономией. Для изменения кода нужен один ответственный исполнитель; независимый сильный ревьюер остаётся обязателен.
- **Управление длинной сессией:** после принятого checkpoint зафиксировать короткую сводку (HEAD, изменённые файлы, RED/GREEN, риски, следующий шаг) в PR/Issue; использовать `/compact` только по необходимости и с сохранением важных ограничений. Не компактировать механически после каждого шага — операция тоже расходует токены.
- **Измерять, не угадывать:** для репрезентативных задач записать доступные `/session` usage/cost и модель/уровень до/после; учитывать cache hit/miss, повторы, стоимость исправлений; не публиковать пользовательские сессии и денежные секреты. Указывать `NOT MEASURED` при отсутствии данных. Не обещать фиксированный процент экономии.
- **Точность важнее экономии:** неизменны GitHub authority, TDD, применимые Skills, безопасность файлов, приватность публичного репозитория, независимое ревью, тестовые гейты и разрешение владельца на merge.

## 6. Обязательные тестовые свойства

- Чтение сессии и ресурсов не меняет их содержимое, дату модификации или семантику.
- Тайм-ауты, отмена, сбой Bridge, потеря потока, дублирующий запрос и восстановление после рестарта тестируются отдельно.
- Обработка конфликтов при одновременном CLI/GUI-использовании не должна терять данные.
- Контракты Bridge версионированы; сообщения и ошибки имеют предсказуемые схемы.
- Установка пакетов и правка MCP требуют подтверждения, проверок и диагностируемого результата.

## 7. Формат отчёта по PR

Каждый PR содержит:

1. Связанный Issue, цель, **точную исходную ветку и SHA**.
2. Перечень изменённых файлов и **статистику строк `+ / -`**, а также сумму по PR.
3. Что реализовано, что сознательно оставлено вне scope.
4. Команды тестов, числовые результаты pass/fail/skip, окружение проверки.
5. Реальный Windows+WSL smoke: `PASS`, `FAIL` или `NOT RUN` — без подмены утверждения.
6. Риски безопасности, изменения пользовательских данных, обратимость, план отката.
7. Вывод независимого ревьюера: `ACCEPT`, `CHANGES REQUIRED`, `BLOCKED`.
8. Список обнаруженных / загруженных / применённых / недоступных Skills и обоснование пропущенных.
9. Изменения `ROADMAP.md`: какие галочки, статусы и записи журнала обновлены; ссылки на принятые PR.
10. **Ресурсы Pi:** фактически использованная модель/уровень `thinking`; `/session` tokens/cost если доступны и раскрытие `NOT MEASURED` иначе; предпринятые меры экономии (без заявлений о непроверенных процентах).

**Без прямого подтверждения владельца не сливать PR в `main`.**

## 8. Начало новой сессии Pi

1. Проверить `AGENTS.md` и текущие `ROADMAP.md`/Issue/PR, прочитать применимые разделы `PRODUCT.md` и `SPECIFICATION.md`; для нового макроэтапа изучить полный контракт, при неизменном контексте не перечитывать одни и те же большие файлы по кругу.
2. Восстановить актуальные Issues/PR/main из GitHub.
3. Обнаружить весь доступный каталог Skills, выбрать и прочитать все применимые `SKILL.md`, зафиксировать выбор.
4. Выбрать ближайший непринятый макроэтап, проверить рабочий каталог, git status и не создавать копий окружения.
5. Выполнить TDD, обновить `ROADMAP.md`, подготовить связный PR с тестами и отчётом по шаблону выше.

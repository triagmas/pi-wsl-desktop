# Как участвовать в разработке

Начните с [README](README.md), [текущей дорожной карты](ROADMAP.md) и задачи в GitHub. [PRODUCT.md](PRODUCT.md) описывает ожидаемое поведение и границы продукта, [SPECIFICATION.md](SPECIFICATION.md) — технические контракты.

## Окружение и запуск

Разработка ведётся в каноническом checkout `F:\_hermes\CODE\pi-wsl-desktop` (в WSL: `/mnt/f/_hermes/CODE/pi-wsl-desktop`), в рабочей ветке. Основная ветка `main` защищена [правилами GitHub](https://github.com/triagmas/pi-wsl-desktop/rules/25366026): изменения проходят через PR, удаление и force push запрещены.

Нужны Windows 11 x64, WSL2 с Ubuntu, существующий Pi в WSL и Node.js **от 22.13.0** с npm в среде, где запускается команда. Для разработки сразу задайте отдельный профиль Desktop:

```powershell
cd F:\_hermes\CODE\pi-wsl-desktop
npm ci
$env:PI_WS_DESKTOP_USER_DATA_DIR = Join-Path $env:TEMP 'pi-wsl-desktop-dev'
npm start
```

`npm start` собирает приложение и открывает Electron. Переменная изолирует настройки **Desktop**, но не подменяет профиль Pi в WSL: приложение может подключиться к существующему Pi. Проверки записи в Pi проводите на синтетических ресурсах; реальные пользовательские данные, model calls и внешние MCP-подключения требуют отдельного разрешения.

Устанавливайте и запускайте зависимости в согласованной среде: Windows и WSL используют разные бинарные пакеты Electron и сборщика. При ошибке native binding сначала проверьте среду запуска; не удаляйте lockfile или все зависимости вслепую.

Для изолированного просмотра интерфейса:

```text
npm run design
http://localhost:5199/?state=showcase
```

[Design Lab](design-lab/README.md) использует демонстрационные данные. Утверждённая библиотека и композиция — источник внешнего вида; при интеграции сохраняйте их и подключайте настоящие данные и действия. Визуальную приёмку владелец проводит отдельно на Windows Electron.

## Подготовка изменения

1. Выберите существующую Issue или согласуйте цель новой. Держите изменение в пределах одной связной задачи.
2. Для изменения поведения сначала воспроизведите проблему тестом, затем внесите исправление и проверьте затронутые сценарии.
3. Обновите документацию и относящийся к задаче статус в [ROADMAP.md](ROADMAP.md). Укажите, что реализовано, что проверено и какая приёмка ещё нужна.
4. Подготовьте PR по [шаблону](.github/pull_request_template.md): цель, ссылка на Issue, состав изменений, проверки и известные ограничения. Независимое ревью и решение владельца предшествуют merge.

Не включайте в коммиты ключи, `auth.json`, `.env`, дампы сессий и приватную конфигурацию. Сохраняйте пользовательские изменения и данные Pi.

## Какие проверки запускать

| Изменение | Проверка |
|:--|:--|
| Только Markdown | Относительные ссылки и якоря, согласованность статусов с GitHub, `git diff --check`, существующий тест `npx vitest run --project unit tests/unit/docsContract.test.ts`; правила CI — в [Repository Contract](.github/workflows/repository-contract.yml) |
| Поведение приложения или контракты | Сначала адресные тесты; перед приёмкой — `npm run typecheck`, `npm run lint`, `npm run build`, `npm test`, `npm run test:e2e` и актуальный Linux/Windows CI |
| Только визуальный слой Lab | TypeScript, lint, build и адресные браузерные проверки изменённых состояний; полный продуктовый набор нужен при изменении поведения или подготовке merge |
| Windows/WSL и выпуск | Дополнительно реальная проверка среды; [M4 и упаковка](docs/release/m4-r01-packaging.md). Использование рабочего профиля и установка — по отдельному разрешению |

Отмечайте фактические `PASS / FAIL / SKIP / NOT RUN`. Успешный CI не заменяет проверку настоящего Pi, реального Windows-окна или визуальную приёмку владельца.

# Pi WSL Desktop

> **Простой Windows-интерфейс для настоящего Pi, работающего внутри WSL.**  
> Чаты, проекты, сессии, Skills, Extensions и MCP — в одном окне, без второй установки Pi и дублирования конфигурации.

**Статус документа:** Product Contract v0.1 · продукт M0/M1 принят, M2 готовится; текущие отметки только в [ROADMAP.md](ROADMAP.md)  
**Платформа:** Windows 11 + WSL2 (Ubuntu — первая целевая среда)  
**Лицензия собственного кода:** MIT  
**Документы:** [Техническая спецификация](SPECIFICATION.md) · [Живая дорожная карта](ROADMAP.md) · [Правила Pi](AGENTS.md) · [Экономия токенов при разработке](docs/TOKEN_EFFICIENCY.md)

## 1. Идея и ценность

**Pi WSL Desktop** — самостоятельный, компактный desktop-клиент для пользователей, которые уже работают с [Pi Coding Agent](https://github.com/earendil-works/pi) в Linux/WSL, но хотят удобный графический доступ к его реальным сессиям и ресурсам.

Продукт **не является новой реализацией Pi**: модели, инструменты, история и расширения остаются под управлением установленного в WSL Pi. Windows-приложение предоставляет интерфейс и надёжный транспорт к этому окружению.

### Ключевое обещание

> Открой приложение, увидь существующие проекты и сессии Pi, продолжи диалог и управляй Skills, Extensions и MCP, не переключаясь между несколькими интерфейсами и не создавая вторую конфигурацию.

### Для кого

- Разработчик, использующий Pi через WSL и несколько проектов.
- Пользователь Pi с множеством Skills, TypeScript Extensions и MCP-серверов.
- Пользователь, которому важны лёгкий клиент, прозрачное управление ресурсами и минимальная инфраструктура.

## 2. Продуктовые принципы

| Принцип | Практический смысл |
|:--|:--|
| **WSL-first** | Вся исполнительная логика Pi остаётся внутри выбранного WSL-дистрибутива. |
| **Pi — единственный источник данных** | Сессии, настройки и расширения не копируются в Windows-хранилище. |
| **Сначала существующие сессии** | Подключение к реальной истории Pi важнее новых украшений интерфейса. |
| **Меньше функций — лучше качество** | Только Chat, Runtime, Resources и необходимые настройки. |
| **Модульность с первого дня** | Границы модулей закладываются сразу; динамическое подключение появится по этапам. |
| **Безопасность изменений** | Просмотр не модифицирует данные; запись только после явного действия. |
| **GitHub — источник истины разработки** | Контракт, Issues, PR, CI и критерии приёмки находятся в репозитории. |
| **Прозрачный прогресс** | Каждый принятый результат отражается в корневом [ROADMAP.md](ROADMAP.md), с доказательством из GitHub. |
| **Контролируемые затраты разработки** | Экономить контекст/токены по сложности задачи, но не снижать качество TDD, безопасность и независимое ревью; [политика](docs/TOKEN_EFFICIENCY.md). Это правило процесса разработки, не отдельный LLM-движок продукта. |

## 3. Что входит в продукт

### 3.1 Sessions & Chat

- Единая боковая панель проектов и сессий, включая **существующие сессии CLI Pi**.
- Поиск по названию, каталогу проекта и доступным метаданным сессии.
- Открытие истории, переключение сессий и продолжение диалога в исходном каталоге.
- Потоковые ответы, отображение работы инструментов, отмена активного запроса.
- Переключение доступных моделей и просмотр состояния исполнения.
- Различение активных, завершённых и недоступных сессий без потери истории.

### 3.2 Pi Runtime

- Выбор установленного WSL-дистрибутива, обнаружение реального Pi и Node.js.
- Постоянное соединение с WSL Bridge, диагностика и переподключение после сбоя.
- Работа с текущими моделями, настройками и SDK/CLI без второго экземпляра конфигурации.
- Явные сообщения об ошибках: нет дистрибутива, Pi не обнаружен, несовместимая версия, ошибка запуска.

### 3.3 Resources Manager

| Раздел | Для первой рабочей версии |
|:--|:--|
| **Skills** | Список, источник, описание, состояние, установка/удаление и обновление доступными средствами Pi. |
| **Extensions** | Установленные пакеты, инструменты и команды, версии, ошибки загрузки, включение/отключение. |
| **MCP** | Глобальные и проектные серверы, состояние, операции настройки, проверка подключения и OAuth по возможностям Pi. |
| **Settings** | Параметры Pi, адреса каталогов, диагностика и настройки интерфейса. |

Изменения конфигурации должны быть видны из **того же Pi CLI**, который пользователь запускает в Ubuntu.

### 3.4 Модульность

- Ядро отвечает за окно, навигацию, соединение, права доступа и базовые UI-компоненты.
- Функции Chat, Sessions, Skills, Extensions, MCP являются обособленными модулями.
- Новые модули смогут добавлять вкладки, панели, действия и визуализации через опубликованный контракт.
- Нельзя требовать изменения ядра при добавлении обычной функции модуля.

## 4. Что **не** делаем

Не включаем в первый продукт: мобильное приложение, браузер с автоматизацией, голосовые функции, встроенную IDE, собственный Git Review, полноценный редактор файлов, отдельный движок моделей, новый формат сессий и облачную синхронизацию.

**Не развиваем инфраструктуру ради инфраструктуры.** Если функция не помогает стабильной работе чатов и ресурсов Pi, она откладывается.

| ID | Сценарий | Ожидаемый результат |
|:--|:--|:--|
| US-01 | Открываю приложение после работы с Pi CLI | Вижу существующие проекты и сессии в WSL. |
| US-02 | Выбираю старый диалог | История корректно отображается; можно продолжить с той же сессии. |

| US-05 | Добавляю MCP-сервер | Его видит Pi CLI; видны статус подключения и ошибки. |
| US-06 | Теряется соединение с WSL | GUI сообщает о проблеме и восстанавливает связь без порчи истории. |

## 6. Критерии успеха версии 1.0

- [ ] Приложение видит рабочий WSL-дистрибутив и установленный в нём Pi.
- [ ] Существующие сессии CLI отображаются **между проектами**; альтернативные каталоги сессий учитываются явно.
- [ ] Старый диалог продолжается в Pi; сообщения читаются из исходного хранилища.
- [ ] Отправка сообщений, потоковый вывод и отмена проверены на Windows + WSL.
- [ ] Skills, Extensions и MCP управляются внутри WSL; Windows-копии конфигурации нет.
- [ ] Сбой транспорта, зависание процесса и перезапуск приложения не повреждают сессии.
- [ ] Неожиданные расхождения с Pi CLI диагностируются, а не замалчиваются.
- [ ] Есть модульные, интеграционные и реальные smoke-тесты Windows + WSL.
- [ ] Публичная сборка содержит документацию, лицензии и не содержит секретов.

## 7. Дорожная карта

| Макроэтап | Пакет | Результат |
|:--|:--|:--|
| **M0** | Foundation & WSL Bridge | Каркас, подключение, health-check, совместимость с текущим Pi. |
| **M1** | Sessions & Chat | Существующие сессии, проекты, история, полноценный диалог. |
| **M2** | Pi Resource Manager | Skills, Extensions, MCP, настройки и диагностика. |
| **M3** | Desktop Module System | Стабильные API модулей, регистрация вкладок/панелей/действий. |
| **M4** | Release 1.0 | Стабилизация, установка Windows, документация, регрессионная приёмка. |

Каждый макроэтап реализуется **одним крупным связным PR или небольшим числом обоснованных PR**, а не десятками микропакетов.

**Текущие статусы, отметки всех принятых задач и журнал выполненного находятся только в [ROADMAP.md](ROADMAP.md).** Данная таблица фиксирует *структуру этапов*, а не их фактическое завершение. В каждом PR необходимо синхронизировать ROADMAP с Issue, diff, тестами и подтверждением приёмки. Документ не может объявлять выполненным незавершённый PR.

## 8. Порядок принятия решений

**Владелец продукта** утверждает цели и финальный merge. **Pi** реализует изменения, применяет TDD и публикует отчёт с тестами. **Независимый ревьюер** проверяет фактический diff, соответствие контракту, риски, результаты CI и количество добавленных/удалённых строк.

Вердикты ревью: `ACCEPT`, `CHANGES REQUIRED`, `BLOCKED`. Даже успешный CI не подменяет продуктовую приёмку.

**Тесты:** Vitest (unit/contract/integration), React Testing Library (UI), Zod (протокол), Playwright + Electron (E2E), реальный Windows+WSL smoke, TypeScript/ESLint. Подробнее — [SPECIFICATION.md §8](SPECIFICATION.md#8-тестирование-и-критерии-приёмки).

**Skills:** Pi проверяет доступный каталог, читает и применяет **все подходящие** навыки по мере необходимости; отчёт об их фактической загрузке и использовании — в PR. Профили сложности модели, компактный контекст и протокол измерений определены в [AGENTS.md](AGENTS.md) и [TOKEN_EFFICIENCY.md](docs/TOKEN_EFFICIENCY.md).

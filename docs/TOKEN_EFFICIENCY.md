# Pi WSL Desktop — экономия токенов при разработке

**Статус:** политика разработки (согласована с Issue #12, подготовлена к приёмке в Issue #14); Pi settings и subagents **не изменены** этим пакетом. Постоянные правила: [AGENTS.md](../AGENTS.md); процедурные инструкции: [pi-desktop-development](../.pi/skills/pi-desktop-development/SKILL.md) и [pi-desktop-review](../.pi/skills/pi-desktop-review/SKILL.md). Только для Pi WSL Desktop Lite.

## 1. Главное: минимальная стоимость принятой задачи

Сравнивать не отдельный вызов LLM, а **общую цену до зелёных тестов и принятого ревью**: запросы + промахи кэша + токены tool outputs + перезапуски + ошибки модели + ревью и доработки. Снижение `thinking` уменьшает возможные reasoning-токены, но может увеличить число ошибок/итераций. Обязательные TDD, Skills, полные финальные проверки и независимый review сокращать **нельзя**.

## 2. Четыре уровня по **типу работы**, не A/B/C-бенчмарк

| Тип задачи | Target thinking | Исполнитель и граница |
|:--|:--|:--|
| Получить status/Issue/PR/CI, git status, точный поиск, механический read | **off** | Основной Pi; только детерминированные операции |
| Документация, небольшая правка текста, отчёты, сортировка задач | **low** | Основной Pi; при неоднозначности эскалация |
| Планирование, анализ требований, выбор тестов, несложная read-only диагностика | **medium** | Основной Pi; если потребуется правка кода → high |
| **Любое создание/изменение кода, TDD, сложная отладка, RPC, rollback, безопасность и архитектура** | **high** | Coding role; предпочитаемая владельцем MiMo 2.6 Flash, если фактически доступна |
| **Независимое ревью реализации** | **high** | Независимый fresh-context review, не self-approval |

Это **целевая политика**, а не автоматическая магия `AGENTS.md`. В Pi и конкретном провайдере могут отличаться запрошенный `thinking`, effective `get_state` и реально поддержанные tiers. При requested ≠ effective — `UNSUPPORTED`/диагностика, а не выдуманный PASS. Проверять доступные levels и mapping на реальной версии Pi. Не объявлять, что `low` и `medium` универсально равны `high`: прежний эксперимент был привязан к одной конкретной среде. Решение по целевым уровням: [Issue #12](https://github.com/triagmas/pi-wsl-desktop/issues/12); ветка PR #13 закрыта без merge, её код не стал частью `main`.

Для source/TDD/review high **не снижать ради экономии**. Остальные установленные релевантные Skills использовать по задаче и не перезагружать неизменные инструкции повторно.

## 3. Как реально настроить Pi

Официальная документация (latest; проверить поддержку **фактически установленной** Pi): [Settings](https://pi.dev/docs/latest/settings), [Configuration](https://pi.dev/docs/latest/configuration), [Compaction](https://pi.dev/docs/latest/compaction), [Sessions](https://pi.dev/docs/latest/sessions), [Skills](https://pi.dev/docs/latest/skills).

Pi поддерживает команды `/model`, `/thinking`, `/settings`; `/session` показывает usage и стоимость, `/compact` уменьшает старый контекст. Настройки живут в `~/.pi/agent/settings.json` (пользовательские) или `.pi/settings.json` в доверенном проекте; проектные настройки влияют на другие задачи в этом каталоге.

**Пример для обсуждения, НЕ применять автоматически** (если подтверждена совместимость Pi и согласовано владельцем):

```json
{
  "defaultThinkingLevel": "low",
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}
```

Здесь 16384/20000 — документированные **значения Pi по умолчанию**, а не заявленная оптимизация и не эксперимент с уменьшением окна. `low` — потенциальный старт для простых задач, **не общее предписание**: для анализа без изменения кода использовать `medium`, для **любого source-code/TDD, безопасности и review — `high`**. Ключ `modelThinkingLevels` можно использовать для поддерживаемых конкретных `provider/modelId` после измерения, не выдумывая ID.

**Важно:** изменение `AGENTS.md` не меняет автоматически `defaultThinkingLevel`, провайдера и расходы. Реальное изменение `settings.json` — только с разрешения владельца, после бэкапа/сравнения фактического файла, без выноса секретов в GitHub. Не создавать `.pi/settings.json` в публичном репозитории только ради экономии до теста совместимости.

## 4. Контекст — самая дешёвая оптимизация без смены модели

1. Начать с `git status --short`, `git log -1 --oneline`, точного Issue/PR и нужных файлов. **Не слать LLM целиком** `git log`, всю ветку PR, большие JSONL и `package-lock.json` без причины.
2. Инвентаризация Skills один раз на сессию/при появлении новых Skills. Pi уже передаёт в prompt **имена и описания**, а полный `SKILL.md` загружается по необходимости. Прочитать инструкции каждого релевантного Skill перед применением; повторно в неизменной сессии не читать весь файл, если он не менялся. Это сохраняет обязательное использование Skills.
3. Для поиска использовать `rg -n` по конкретному пути/символу, затем диапазон строк; типично показывать контекст вокруг ошибки, а не весь файл. Исключение — первый архитектурный обзор, если весь исходник действительно нужен.
4. Тесты в Red→Green: сначала узкая `vitest` suite/один файл, **затем обязательно** полный стек в финальном acceptance: `typecheck`, `lint`, `build`, Vitest, E2E, GitHub CI и отдельно реальный Windows+WSL smoke. Если тест ошибся — анализировать полный локальный лог, в контекст передавать статус, failing assertions и нужные строки.
5. На границах этапов фиксировать короткий handoff: `issue`, `branch/HEAD`, затронутые файлы, открытые риски, TDD RED/GREEN, next action. Разумно начать новую Pi-сессию со ссылками на GitHub и handoff, если старая обросла нерелевантной историей.
6. Использовать `/compact` после проверки, что сводка сохранит ограничения, исходные SHA, неслитые файлы и TODO. Не вызывать ради каждого маленького патча: сам вызов compaction тоже расходует модельные токены.
7. Subagent получает **узкий diff и критерии**, а не бесконечную историю проекта. Сравнивать совокупную стоимость подагент+основной агент с работой без делегирования.

**Нельзя оптимизировать ценой риска:** пропуск security ревью, невыявленные изменения настоящих сессий Pi, запись в защищённый `main`, реальный model-call без согласия, публикация секретов, подмена `NOT RUN` на PASS, пакетирование фиктивных тестов.

## 5. Измерение только в обычных разрешённых задачах

Никаких искусственных платных серий A/B/C, model prompt или изменения активных настроек ради проверки таблицы. При выполнении обычной авторизованной работы можно **пассивно** фиксировать `task_type → target thinking → effective thinking → result`, количественные данные `/session`, число повторов, тесты и review. Только если известен baseline конкретной задачи, считать её стоимость; иначе `NOT MEASURED`.

Частный provider/model ID, `~/.pi/agent/settings.json`, токены/сессии и внешние credentials не публиковать в публичный GitHub. Успех `AGENTS.md`/Skills-пакета подтверждает корректность документов и discovery, но **не** работу нативной автоматической маршрутизации. Существующий локальный Extension не меняется этим PR. Отдельные permission gates на real Pi calls и user data сохраняются.

## 6. Граница с продуктом

Правила выше оптимизируют **разработку проекта через Pi**, а не создают отдельный маршрутизатор моделей внутри Pi WSL Desktop. В продукте можно отображать существующие настройки модели/effort/cost в режиме чтения, **если реальный Pi API это поддерживает**. Любое переключение модели и глобальных параметров в UI должно быть явным, видно в Pi CLI, проверено на установленной версии и не смешано с ресурсным менеджером без необходимости.

**Приёмка процесса:** четыре целевых уровня задокументированы, проектные Skills добавлены в отдельной Draft-ветке. Фактическая совместимость с локальным Pi, автоматическое применение, реальная экономия токенов **пока NOT RUN / NOT MEASURED**, пользовательские настройки не изменены. Это не продуктовая фича Desktop.

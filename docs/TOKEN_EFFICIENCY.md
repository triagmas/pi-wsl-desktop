# Pi WSL Desktop — экономия токенов при разработке

**Статус:** принятая исходная политика из M2 PR #8; её уточнение о реальном `off/low/medium/high`-роутинге готовится в [Draft PR #13](https://github.com/triagmas/pi-wsl-desktop/pull/13). Пользовательская конфигурация Pi **не изменялась**. Источник обязательных правил: [AGENTS.md §5.1](../AGENTS.md). Применять к Pi WSL Desktop, **не** распространять на VoiceForge/ChatWake/другие проекты.

## 1. Главное: минимальная стоимость принятой задачи

Сравнивать не отдельный вызов LLM, а **общую цену до зелёных тестов и принятого ревью**: запросы + промахи кэша + токены tool outputs + перезапуски + ошибки модели + ревью и доработки. Снижение `thinking` уменьшает возможные reasoning-токены, но может увеличить число ошибок/итераций. Обязательные TDD, Skills, полные финальные проверки и независимый review сокращать **нельзя**.

## 2. Назначение model role / thinking по виду задачи

**Цель — распределять реальные задачи, а НЕ проверять семь коротких платных запросов.** Следующие уровни — целевой процесс оркестрации; перед каждой работой запрашивать их **настоящим механизмом Pi** и сверять effective level, когда это поддерживается.

| Класс | Конкретная работа | Роль модели | Thinking |
|:--|:--|:--|:--|
| A — механический | GitHub status, Issue/PR/CI, точные команды, поиск, git diff --stat | PRIMARY | **`off`** |
| B — лёгкий | Документация, небольшие отчёты, шаблонные правки и сортировка задач | PRIMARY | **`low`** |
| C — аналитический | Планирование, анализ требований, выбор тестов, первичная диагностика | PRIMARY | **`medium`** |
| D — инженерный | **Любое написание/изменение кода**, TDD, багфиксы, сложная отладка | CODING (предпочтительно MiMo 2.6 Flash) | **`high`** |
| E — критичный | Архитектура, безопасность, concurrency, Pi RPC, rollback | CODING/qualified specialist | **`high`** |
| F — проверочный | Независимое ревью исходного кода, release/security gate | независимый REVIEW | **`high`** |

Если работа класса A/B/C превращается в изменение кода либо security-sensitive действие, **повысить до high ДО действия**. Простое описание тест-плана может готовиться на medium, а TDD-редактирование тестов и реализации — high. Для code review нужен независимый свежий контекст, даже если исполнитель работал high.

**Важное различие:** `off/low/medium/high` — целевые уровни, поддерживаемые Pi как система, но конкретная модель, прокси или `thinkingLevelMap` могут ограничивать фактический выбор. `get_state.thinkingLevel=high` после requested `low` — наблюдение о Pi runtime/mapping, **не измерение reasoning-токенов у провайдера** и не основание выбрасывать `low/medium` из общей схемы. Нужны реальные Pi CLI/RPC readback и проверка level map, а не короткий оплачиваемый prompt.

**Prompt cache:** cached input-prefix, cache warming и фиксированный системный контекст могут делать похожими стоимость/ответы коротких задач. Ответ из такого сравнения не доказывает ни равенства thinking, ни процент экономии. Сравнивать `requested level`, `effective level`, `provider mapping`, `cacheRead/cacheWrite` и измеренный reasoning usage **раздельно**; без доступного сигнала писать `NOT VERIFIED`.

## 3. Как реально настроить Pi

Официальная документация (latest; проверить поддержку **фактически установленной** Pi): [Settings](https://pi.dev/docs/latest/settings), [Configuration](https://pi.dev/docs/latest/configuration), [Compaction](https://pi.dev/docs/latest/compaction), [Sessions](https://pi.dev/docs/latest/sessions), [Skills](https://pi.dev/docs/latest/skills).

Pi поддерживает команды `/model`, `/thinking`, `/settings`; `/session` показывает usage и стоимость, `/compact` уменьшает старый контекст. Настройки живут в `~/.pi/agent/settings.json` (пользовательские) или `.pi/settings.json` в доверенном проекте; проектные настройки влияют на другие задачи в этом каталоге.

**Пример для обсуждения, НЕ применять автоматически** (если подтверждена совместимость Pi и согласовано владельцем):

```json
{
  "defaultThinkingLevel": "low",
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}
```

Здесь 16384/20000 — документированные **значения Pi по умолчанию**, а не заявленная оптимизация и не эксперимент с уменьшением окна. `low` подходит для лёгких документов; `medium` — для анализа и планов; **код/TDD/безопасность/review — `high`**. Это иллюстрация значений настройки, а не команда автоматически установить `low` пользователю. Ключ `modelThinkingLevels` можно использовать для поддерживаемых конкретных `provider/modelId` после измерения, не выдумывая ID.

**Важно:** изменение `AGENTS.md` не меняет автоматически `defaultThinkingLevel`, провайдера и расходы. Реальное изменение `settings.json` — только с разрешения владельца, после бэкапа/сравнения фактического файла, без выноса секретов в GitHub. Не создавать `.pi/settings.json` в публичном репозитории только ради экономии до теста совместимости.

## 4. Контекст — самая дешёвая оптимизация без смены модели

1. Начать с `git status --short`, `git log -1 --oneline`, точного Issue/PR и нужных файлов. **Не слать LLM целиком** `git log`, всю ветку PR, большие JSONL и `package-lock.json` без причины.
2. Инвентаризация Skills один раз на сессию/при появлении новых Skills. Pi уже передаёт в prompt **имена и описания**, а полный `SKILL.md` загружается по необходимости. Прочитать инструкции каждого релевантного Skill перед применением; повторно в неизменной сессии не читать весь файл, если он не менялся. Это сохраняет обязательное использование Skills.
3. Для поиска использовать `rg -n` по конкретному пути/символу, затем диапазон строк; типично показывать контекст вокруг ошибки, а не весь файл. Исключение — первый архитектурный обзор, если весь исходник действительно нужен.
4. Тесты в Red→Green: сначала узкая `vitest` suite/один файл, **затем обязательно** полный стек в финальном acceptance: `typecheck`, `lint`, `build`, Vitest, E2E, GitHub CI и отдельно реальный Windows+WSL smoke. Если тест ошибся — анализировать полный локальный лог, в контекст передавать статус, failing assertions и нужные строки.
5. На границах этапов фиксировать короткий handoff: `issue`, `branch/HEAD`, затронутые файлы, открытые риски, TDD RED/GREEN, next action. Разумно начать новую Pi-сессию со ссылками на GitHub и handoff, если старая обросла нерелевантной историей.
6. Использовать `/compact` после проверки, что сводка сохранит ограничения, исходные SHA, неслитые файлы и TODO. Не вызывать ради каждого маленького патча: сам вызов compaction тоже расходует модельные токены.
7. Subagent получает **узкий diff и критерии**, а не бесконечную историю проекта. Сравнивать совокупную стоимость подагент+основной агент с работой без делегирования.

**Нельзя оптимизировать ценой риска:** пропуск security ревью, невыявленные изменения настоящих сессий Pi, запись в защищённый `main`, реальный model-call без согласия, публикация секретов, подмена `NOT RUN` на PASS, пакетирование фиктивных тестов.

## 5. Проверка назначения thinking и учёт расходов

**Приёмочный критерий политики:** не цена короткого теста, а корректная маршрутизация `task_type → role → requested thinking → Pi effective thinking → outcome` **для реальных задач**. Тесты маршрута должны быть **без внешних model calls**: один disposable Pi, readback уровня (где доступно), негативные/эскалационные ветки, проверка что coder/high не наследует предыдущий `off`.

- `off`: status/механическая задача; `low`: простая документация; `medium`: планирование/анализ; `high`: код/TDD, безопасность и независимое ревью.
- Если requested/effective расходятся, выяснить модельные настройки и совместимость Pi, не маскировать fallback. Не менять пользовательский provider/model или `settings.json` ради теста.
- Реальные token/usage/cost можно **пассивно** собирать на обычных разрешённых задачах. Выделять cacheRead/cacheWrite, retries, повторы, количество успешных работ и TDD/review loops. Финансовую экономию отмечать `NOT MEASURED`, пока нет сравнимых данных.
- **Не запускать 6/7 платных A/B/C экспериментов**: предыдущий план отменён. Внешние model-calls требуют отдельного явно указанного разрешения и бюджета, а не права на смену режима мышления.

## 6. Граница с продуктом

Правила выше оптимизируют **разработку проекта через Pi**, а не создают отдельный маршрутизатор моделей внутри Pi WSL Desktop. В M2 можно отображать существующие настройки модели/effort/cost в режиме чтения, **если реальный Pi API это поддерживает**. Любое переключение модели и глобальных параметров в UI должно быть явным, видно в Pi CLI, проверено на установленной версии и не смешано с ресурсным менеджером без необходимости.

**Приёмка процесса:** маршрутизация задач по четырём уровням — отдельная проверяемая функция процесса; **ещё не доказано** её фактическое применение в живом Pi. Экономия денег **NOT MEASURED**. Настоящие default settings, пользовательские сессии и модельные вызовы не менялись/не выполнялись в рамках новой политики.

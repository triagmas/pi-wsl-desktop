## Fast Development: уровень QA выбирается до начала работы

Правило владельца (2026-11-02): объём проверок пропорционален реальному риску. Перед первой правкой Pi указывает одну строку — `QA level: V|F|B|R; почему; что намеренно не запускаем` — и дальше не расширяет проверки без названной причины.

| Уровень | Условия | Проверки при итерации | Намеренно НЕ запускается |
|---|---|---|---|
| **V — визуальное** | CSS, размеры, цвет, типографика, раскладка, документация без изменения runtime | Скриншоты затронутых состояний BEFORE/AFTER (2–4 кадра) либо адресная проверка документации; typecheck/lint только если затронуты `.ts/.tsx` | Полный Vitest, весь E2E, installer, packaged smoke, все DPI, сборочный EXE «на всякий случай» |
| **F — локальное поведение UI** | Кнопка, выбор проекта, состояние composer, локальный рендер | RED→GREEN адресный unit/UI-тест + затронутый E2E-сценарий; typecheck/lint по затронутым файлам | Полная регрессия, installer, CI-эмуляция, чужие E2E |
| **B — контракты и данные** | Bridge, Pi RPC, IPC/Preload, сессии, таймауты, persistence, безопасность | TDD/контрактные и интеграционные тесты затронутых модулей, негативные сценарии, Windows↔WSL smoke при риске реального поведения | Проверки несвязанных подсистем; полный набор — только если изменение cross-cutting |
| **R — интеграция / merge / release** | Подготовка merge, релиз, изменение гейтов и CI | Полный необходимый релевантный набор: typecheck, lint, build, `npm test`, `npm run test:e2e`, CI, packaging/smoke | Ничего из обязательного релизного контракта; только явно непроведённое → `NOT RUN` |

Правила применения:

- Полный прогон нельзя назначать «потому что он существует». Основание для R — merge/release или названный cross-cutting риск.
- **Эскалация по границе:** если правка выходит за уровень (CSS задел кликабельность/доступность, локальный UX задел управление Pi RPC), повышается уровень **затронутой области** с объяснением, а не запускается всё подряд.
- Повторный запуск уже доказанного результата на неизменённых файлах не является проверкой.
- Артефакты минимальны: обычная итерация — несколько скриншотов и короткая сводка; ZIP/EXE — только когда владельцу нужен реальный Windows-экран или затронут packaging.
- Независимый review — на законченный пакет или pre-merge, а не на каждый микропатч.
- Безопасность, согласие владельца на запись/merge и запрет на платные вызовы не зависят от уровня и не ослабляются.

### Примеры маршрутизации (сухие решения, без запуска)

| Задача | Уровень | Что запускаем | Что намеренно не запускаем |
|---|---|---|---|
| Уменьшить размер текста предпросмотра шрифта | **V** | адресный `tests/ui/*preview*` при затронутом TSX + 1–2 скриншота раздела «Типографика» | полный Vitest, Electron E2E, build, installer |
| Исправить выбор проекта для «Нового диалога» | **F** | RED→GREEN адресные UI-тесты выбора проекта + затронутый E2E | полный набор, installer, CI-эмуляция |
| Изменить таймаут Pi RPC | **B** | unit-тесты бюджетов/таймаутов + интеграционный тест моста, негативные сценарии | визуальные проверки, полный E2E, DPI/скриншоты |
| Подготовка продукта к merge/release | **R** | typecheck, lint, build, `npm test`, `npm run test:e2e`, CI, Windows packaging/smoke | ничего сверх релизного контракта; непроведённое — `NOT RUN` |

### Отчёт обычной итерации (V/F/B)

1. Что изменено и какие файлы затронуты. 2. `QA level`. 3. Какие адресные проверки прошли. 4. Что намеренно не выполнялось. 5. Оставшиеся проблемы. 6. `+/-` строк. Для визуальной правки достаточно нескольких релевантных скриншотов. Развёрнутая evidence-матрица нужна только на R и для high-risk пакетов.

## Quality Code: Issue #35 / Draft PR #36 (Q1–Q4)

Раздел фиксирует состояние Quality Code как есть; он не является разрешением менять workflow, статусы или PR без отдельного решения владельца.

### Без новых платных подписок

- Новый Q1: GitHub CodeQL для `javascript-typescript` на публичном репозитории; стандартные GitHub-hosted runners и встроенные GitHub Code Scanning alerts. Нет LLM, API-ключей, регистрации в SaaS и доступа к пользовательскому Pi.
- Существующие: `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:e2e`, `npm run build`, Windows installer/packaged smoke, `prek` и Repository Contract. **Не дублировать** тестовые запуски в Q1.
- CodeRabbit/другие GitHub Apps: этим PR **не устанавливались**. App подключён владельцем отдельно; бесплатные квоты не означают отсутствие передачи данных третьей стороне.
- Подписки/модельные лимиты Pi не используются. Реальные вызовы AI запрещены без отдельного разрешения владельца по `AGENTS.md`.

### Q1 — CodeQL (пилот)

Файл: [`.github/workflows/quality-codeql.yml`](../../.github/workflows/quality-codeql.yml) — появляется вместе с этим документом в PR #36; после merge в `main` ссылка рабочая, до этого файла локально нет.

Запуск на PR к `main`, push в `main` и вручную (`workflow_dispatch`). Право `security-events: write` требуется только этому workflow для загрузки результатов CodeQL; остальные полномочия минимальные. GitHub Actions закреплены по commit SHA. Платформозависимые Windows/WSL smoke здесь **не запускаются**.

**Режим CodeQL — взаимоисключающий.** Нельзя одновременно держать включёнными **Default Setup** и **Advanced Setup** из этого workflow: при включённом Default Setup GitHub **блокирует загрузку SARIF** из Advanced Setup, то есть анализ формально «прошёл», а результаты в Code Scanning не попадают. Перед merge и перед повторным запуском выбирается **ровно один** режим: оставить Default Setup и не использовать этот workflow, либо оставить Advanced Setup (текущее состояние). Настройки GitHub мы не меняем — это делает только владелец.

**Текущее состояние (проверено read-only API 2026-11-02, настройки не менялись):**

- `GET /repos/{owner}/{repo}/code-scanning/default-setup` → `state: "not-configured"` — **Default Setup выключен**, риск блокировки загрузки отсутствует; работает только Advanced Setup из `quality-codeql.yml`.
- В Code Scanning одна единственная analysis: `.github/workflows/quality-codeql.yml:analyze`, ref `refs/pull/36/merge`, `results_count: 0`, `rules_count: 87`, CodeQL 2.27.3, `error: ""`.
- Два разных check-имени на PR #36 — это **один** workflow, а не два режима: `CodeQL` (`app=github-advanced-security`, workflow-уровень) и `CodeQL - JavaScript/TypeScript` (`app=github-actions`, сам analyze-джоб). Дублирования анализов нет.

Проверка Q1 на GitHub:

1. Открыть Draft PR; посмотреть `Quality - CodeQL / CodeQL - JavaScript/TypeScript`, `Product CI` и `Repository Contract`.
2. Зафиксировать SHA и конкретные статусы всех jobs: PASS / FAIL / SKIP / NOT RUN. Для проблем с разрешениями на Code Scanning — не обходить их, открыть блокер.
3. Просмотреть Code Scanning findings, классифицировать новые actionable vs false positive, указать путь, строку, severity и remediation.
4. Независимый review, затем только **отдельное явное разрешение владельца** на merge. Workflow не включает auto-merge и не меняет required checks/branch protection.

### Q2 — архитектура (ещё не реализована)

Пилот `Knip` и `dependency-cruiser` в **report-only**: сначала установить фиксированные версии с обычной процедурой `npm install -D`, коммитить lockfile, измерить число реальных находок и ложных срабатываний для dynamically loaded modules. Только после согласования правил сделать blocking gate. Архитектурный критерий: renderer не должен импортировать привилегированные `main`/`bridge`/`node:` модули; контракт IPC/Preload сохраняется. Проверять также циклы; не запрещать обоснованные `shared` типы.

### Q3 — проверка качества тестов/UI (ещё не реализована)

`Stryker` только на ограниченном критичном модуле (history merge / IPC / session safety), замерить mutation score, время и flaky tests; не включать полный mutation-run в каждый PR без измерений. `Playwright` screenshot regression после утверждения эталона владельцем, с фиксированными DPI, ОС, шрифтами и состояниями. `axe-core/playwright` — accessibility, но не замена визуальной приёмки.

### Q4 — оценка Harness² (отдельный пакет, ещё не реализован)

10–15 повторяемых задач; запись `task_id`, базовый SHA, модель/provider, available Skills, токены, число tool calls, correctness, permission violations и evidence. Сравнение с baseline при **той же** модели и бюджете; запрещено выдавать self-review за независимую приёмку. Бесплатный eval-runner или promptfoo Community допустимы только после оценки стоимости внедрения. Никаких дополнительных платных API.

## Политика результата

Каждый gate обязан сообщать: **какой риск он реально покрывает**, набор файлов, baseline, measured runtime, найденные дефекты, false positives и rollback. Отсутствие проверки = `NOT RUN`, а не `PASS`. CI не подтверждает качество реального Windows+WSL интерфейса или безопасность при любых сценариях. Отсутствие полного прогона на уровне V/F — это соблюдение процесса, а не пробел в evidence, если уровень задекларирован и адресные проверки выполнены.

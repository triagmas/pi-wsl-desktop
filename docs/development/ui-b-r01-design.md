# UI-B R01 — терминал WSL и метрики Windows: технический выбор

Статус: реализация в работе по Issue [#21](https://github.com/triagmas/pi-wsl-desktop/issues/21) (UI-B), QA level **B + F** (адресные тесты, полная регрессия — в интеграционном CI).
База: `main` `0a8afa99` (PR #34 squash-merged).

## 1. Терминал: PTY

**Выбор.** PTY создаётся **внутри выбранного WSL-дистрибутива** небольшим помощником на `python3` (stdlib `pty`/`fcntl`/`termios`), который запускает main-процесс через отдельный `wsl.exe -d <distro> --exec python3 -u -c <runner> <b64-скрипт> <cols> <rows> <cwd> <shell>`.

Почему так:

- **Реальный PTY, а не пайп.** `wsl.exe` с обычными pipe не даёт TTY: bash теряет job control, программы считают себя неинтерактивными. `os.forkpty()` даёт настоящий `/dev/pts/N`, поэтому работают цвета, Ctrl+C, `less`, `top`, `stty`, readline.
- **Resize.** Размер меняется `ioctl(TIOCSWINSZ)` на master-PTY + `SIGWINCH` ребёнку; проверено вживую (`stty size` → `24 80` и после resize → `40 120`).
- **Без тяжёлых зависимостей.** Ни `node-pty` (нативный модуль + rebuild под ABI Electron + ConPTY только на стороне Windows), ни `tmux`/`socat` не нужны. Используется то, что уже есть в Ubuntu WSL: `python3` (stdlib) и `/bin/bash`.
- **Изоляция транспорта.** Терминал — **отдельный процесс** `wsl.exe`, не связанный с Pi RPC-мостом: падение/закрытие терминала не трогает Pi-сессию, а терминал не может отправлять RPC-методы Pi. Renderer не получает ни Node.js, ни произвольный shell IPC — только 4 типизированных вызова и события.
- **Никакого скрытого исполнения.** Процесс стартует только по явному действию пользователя (кнопка/вкладка); при запуске приложения shell-команды не выполняются, из ответов модели ничего не подставляется.

Протокол (NDJSON поверх stdin/stdout процесса):

| Направление | Кадры |
|---|---|
| main → helper | `{"t":"in","d":"<base64>"}`, `{"t":"resize","c":N,"r":N}`, `{"t":"close"}` |
| helper → main | `{"t":"ready","pid":N,"cwd":"/p"}`, `{"t":"out","d":"<base64>"}`, `{"t":"notice","code":"CWD_FALLBACK","message":"…"}`, `{"t":"exit","code":N}` |

Base64 обязателен: вывод PTY может разрезать UTF-8 последовательность, байтовая точность важнее текстовой.

Проверки безопасности и границ:

- содержимое скрипта — константа, передаётся base64 и не интерполируется (нет инъекции через distro/cwd);
- `distro` валидируется по безопасному шаблону, `cwd` — абсолютный POSIX-путь без NUL/переводов строк; невалидные значения отклоняются (`TERMINAL_BAD_CWD`), а не «исправляются молча». Пустая строка — не ошибка, а «проекта нет»: домашний каталог плюс заметка `CWD_FALLBACK`;
- недоступный каталог проекта → помощник остаётся в домашнем каталоге и присылает `notice CWD_FALLBACK` (видимое объяснение, не тихий переход);
- лимит сессий, лимит кадра и чанка, отсутствие «бесконечного» буфера;
- закрытие вкладки завершает только процесс этой сессии (`SIGHUP` ребёнку); при закрытии приложения — только собственные процессы терминала, без глобального `wsl --shutdown`/`--terminate`;
- если `python3` или `pty` недоступны — честная ошибка `TERMINAL_UNAVAILABLE` с текстом причины, без фиктивного вывода.

Риски:

1. Зависимость от `python3` в дистрибутиве (в Ubuntu WSL есть по умолчанию). При отсутствии — явная ошибка, терминал не «делает вид».
2. Логин-шелл (`bash -l`) может печатать приглашения/баннеры профиля — это реальный вывод пользователя, не выдуманный.
3. `forkpty` под Windows-обёрткой `wsl.exe` не тестировался на не-Ubuntu дистрибутивах; проверка — при живом прогоне на конкретной машине (в этой итерации Linux/Ubuntu).

## 2. Метрики: CPU/RAM Windows

**Выбор.** Значения считает **main-процесс** через встроенный модуль `node:os`: `os.cpus()` (накопительные времена по ядрам → прирост за интервал) и `os.totalmem()/os.freemem()`. Renderer запрашивает готовый снимок через типизированный IPC `metrics:get`.

- Никаких `wmic`/PowerShell/`systeminfo` на каждый опрос и никаких внешних зависимостей.
- CPU% = `100 × (1 − Δidle/Δtotal)` между двумя опросами; первый опрос отдаёт `null` (в UI — «—»), а не выдуманный ноль.
- Защита от частых вызовов: минимальный интервал между пересчётами (кэш последнего снимка).
- Опрос из renderer: интервал ≈ 2 c, single-flight (следующий запрос только после ответа), пауза при `document.hidden`, немедленное обновление при возврате окна.
- Недоступные/некорректные значения → `null` → «—».

Риски: `os.cpus()` даёт системные времена хоста (то, что нужно: «Windows», не Ubuntu и не процесс Pi); при сильной нагрузке одного ядра проценты считаются по сумме — стандартное поведение диспетчера задач.

## 4. Что выяснилось на живом прогоне (Windows → WSL)

Проверка на реальном приложении (9 сценариев, 0 падений) вскрыла четыре вещи, которые нельзя было увидеть в jsdom:

1. **Первый `fit` проигрывал гонку с раскладкой.** PTY открывался 80×24 и оставался таким, потому что `onResize` подписывался уже после первого `fit.fit()`, а больше размер не менялся. Теперь обработчик ставится до фитинга, после открытия отправляется явная синхронизация `terminal.resize(cols, rows)`, плюс повторные фитинги в следующем кадре и через 250/800 мс.
2. **Слот-заглушка забирал половину дока.** `.dl-terminal .terminal-slot { flex: 1 }` в живом режиме делил высоту с PTY, поэтому терминал оставался в 5–6 строк. В `.dl-term-body-live` слот убран из раскладки.
3. **Подпись-заметка тоже была `flex: 1`.** Уведомление о потере cwd (`dl-term-note`) занимало половину дока; в живом режиме оно компактное (`flex: 0 0 auto`, 12 px).
4. **cwd без проекта.** Пустой cwd — это не ошибка: помощник открывает домашний каталог и присылает видимую заметку «Проект недоступен: терминал открыт в домашнем каталоге». Молчаливой подстановки `/` больше нет.

Зафиксированный результат при живом прогоне: `stty size` = фактическому размеру дока (10×93 при 1000×720 и открытом доке), после изменения высоты дока — 16×93; `$SHELL` → `/bin/bash`, `pwd` → `/home/triag`; метрики — «CPU 32%», «RAM 30,4 / 31,1 ГБ» с обновлением раз в ~2 с.

## 5. Жизненный цикл: скрытие дока, закрытие, освобождение

- **Процесс принадлежит сессии, а не панели.** Док терминала остаётся смонтированным при скрытии (хост с `display: contents` и атрибутом `hidden`), поэтому вкладки и живой PTY не теряются. Скрыть док ≠ закрыть терминал.
- **Закрытие вкладки** отправляет кадр `close`, затем закрывает stdin помощника: EOF для него равен «закрыть PTY», он сам снимает `SIGHUP` с ребёнка и выходит, освобождая дескрипторы. Если за `killGraceMs` (1.5 c) процесс не ушёл — `SIGKILL` только этому `wsl.exe`.
- **Закрытие приложения** (`before-quit` → `disposeAll`) завершает только собственные процессы терминала; глобальные `wsl --shutdown`/`--terminate` не используются.
- **Закрытие во время выполняющейся команды** убивает только эту сессию. UI не показывает фиктивного «успешно завершено»: вкладка исчезает, приложение остаётся работоспособным, лимит сессий освобождается сразу — новая вкладка открывается без ожидания.
- **Адресность.** Все операции идут по `id` сессии из main-процесса: неизвестный/пустой `id` — no-op (`write` → `false`), закрытие одной сессии не влияет на остальные. Renderer не может обратиться к произвольному процессу, указать свой PID или выполнить shell-строку.

## 6. Границы пакета

- Реальные Pi-сессии, `~/.pi`, настройки провайдеров/моделей, MCP не затрагиваются.
- Существующие IPC-контракты (`bridge:*`, `appearance:*`, `window:*`) не меняются; терминал и метрики — отдельные каналы.
- Layout не меняется: док остаётся в центральной колонке между композером и статус-баром.

## 7. Что не проверено (NOT RUN)

- Несколько одновременных терминальных вкладок в живом окне (лимит и переключение покрыты юнит-тестами, живьём открывалась одна вкладка за раз).
- Аварийное отключение WSL во время сессии (`wsl --terminate`, падение дистрибутива): сценарий потери процесса покрыт юнит-тестом, живой обрыв не воспроизводился.
- DPI 100/125/150/200 %, вторая мониторная конфигурация.
- Установленная сборка (NSIS-инсталлятор) и работа в рабочем Windows-профиле.
- Полный Vitest, весь Electron E2E, установщик и полный CI — выполняет GitHub CI, локально запускались только адресные наборы.
- Дистрибутивы WSL, отличные от Ubuntu (в частности, отсутствие `python3`).

## What it is

A Windows desktop client for the **existing** Pi Coding Agent inside WSL.
Pi itself, its sessions, its settings and its extensions stay in the Linux
distribution; the application is an interface on top of the documented
Pi CLI/RPC and a WSL bridge. It is not an official Pi product and does not
re-implement Pi.

## Highlights in 1.0

- **Chat with a real Pi session** — streaming answers, stop/abort, projects,
  session list, history restored from the original Pi JSONL files
  (read-only; nothing is copied to Windows).
- **New chat through the official `new_session`** — the session file is
  created by Pi on the first message; the desktop keeps drafts separately.
- **Resource manager** — Skills, packages/extensions and MCP configuration
  with preview, explicit confirmation, backup and rollback of every write.
- **Declarative modules** — external manifests with tabs, panels and actions;
  enabled/disabled state persisted in the bridge home.
- **Real WSL terminal (PTY)** — a real `/dev/pts` session in the selected
  distribution under the chat area: typing, output, resize, tabs, close.
  The terminal survives hiding the dock and switching screens.
- **Real Windows host metrics** — CPU load and used/total RAM of the Windows
  host in the status bar (~2 s poll, paused when the window is hidden).
- **Design system** — five themes (Dark, Light, Claude Code, Codex, Custom
  with an editor) and per-zone typography.
- **Windows installer (NSIS)** — per-user one-click install, no elevation,
  ownership guard against foreign install directories, user data preserved
  on update and uninstall.

## Requirements

- Windows 10/11 x64.
- WSL2 with at least one distribution; the verified distribution is **Ubuntu**.
- Pi Coding Agent installed and configured **inside** that distribution
  (the app does not install or configure Pi for you).
- **Node.js inside that distribution: 22.19.0 or newer.** The desktop starts its
  WSL bridge with the `node` found there (searched in `PATH` without a login
  shell, then `~/.local/bin`, `/usr/local/bin`, `/usr/bin`) and fails with
  `NODE_NOT_FOUND` when it is missing. Pi 1.5.0 itself requires
  `node >= 22.19.0`; this package declares `>= 22.13.0`, so the stricter Pi
  requirement is the effective one. The desktop does not gate the connection
  on a minimum Node version — check it yourself with `node --version` in the
  distribution; an outdated Node fails when the bridge starts.
- **Python 3 inside the distribution** — required *only* by the terminal dock
  (a stdlib-only PTY helper). Node serves the bridge and the chat; Python 3
  serves the terminal. Without Python 3 the app runs and the terminal reports
  `TERMINAL_UNAVAILABLE` honestly.
- A shell (`bash` or the login shell) for the terminal.

Preflight, run inside the distribution:

```bash
node --version    # v22.19.0 or newer
python3 --version # any 3.x, terminal only
pi --version      # Pi is installed and on PATH
```

## Data and privacy

- Existing Pi sessions are read in place and are not copied or converted.
- The application does not see or store provider credentials; Pi keeps them.
- No telemetry and no outbound listener; the only network traffic is the one
  Pi itself performs.
- Resource operations write into the Pi home only after explicit confirmation,
  with a backup and a rollback path.

## Upgrade from 1.0.0-rc.1, and downgrade

The application does **not** archive previous installers and has no update
channel: nobody but you keeps a copy of the version you are leaving. Before
upgrading:

1. Save the installer you are currently using together with its SHA-256 in an
   archive folder outside the install directory — this copy is the only
   rollback target.
2. Copy `%APPDATA%\pi-wsl-desktop` (the user data directory: window layout,
   appearance, drafts, cached module state).
3. Install the newer version over the old one.

**Downgrade is not guaranteed to be data-compatible.** Installing a newer
version keeps the user data directory, but the older version is not obliged to
understand state written by a newer one. If a downgrade starts with a broken
window or empty-looking state, close the app and restore the backup taken in
step 2; if the app refuses to start, move the data directory aside and let it
recreate a fresh one. No Pi data is involved in any of these steps. The exact
backup target and failure modes are listed in
[1.0.0-install-rollback.md](1.0.0-install-rollback.md).

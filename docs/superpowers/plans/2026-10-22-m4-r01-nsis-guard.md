# M4 R01 Security Closure — NSIS /D= protection (variant B) — Plan

Owner decision: variant B — close the `/D=` install-dir footgun with a
minimal, allow-listed NSIS include, keeping the standard electron-builder
26.15.3 lifecycle. Issue #16; PR #20; NOT mixed with UI redesign #21.

## Research facts (electron-builder 26.15.3, verified in node_modules)

- `installer.nsi:.onInit` inserts `initMultiUser` (computes `$INSTDIR`
  incl. the `/D=` override — `multiUser.nsh:50-54/94-96`) and THEN the
  `customInit` macro (`installer.nsi:76-81`) — a `customInit` guard runs
  before ANY file operation, in silent and interactive modes alike.
- `nsis.include` is compiled into the preamble via
  `NsisScriptGenerator.include` and does NOT replace the template
  `include/installer.nsh` (pulled separately by `installSection.nsh:1`)
  as long as our file has a DIFFERENT filename → a guard include only
  ADDS macros; the standard lifecycle templates stay untouched.
- `customInstall` runs in the install section after files are extracted
  (`installSection.nsh:81`) — the place to (re)write the ownership marker
  on every install/upgrade.
- `customUnInstall` runs before the uninstaller deletes anything
  (`uninstaller.nsh:156`), before the default `RMDir /r $INSTDIR`
  (`uninstaller.nsh:187`) — the place for an ownership check that quits
  the uninstall when the marker is missing (fail-safe: keep the dir).

## Design

One new file `build/nsis-guard.nsh` (include-guarded), wired as
`build.nsis.include: "nsis-guard.nsh"` (buildResources lookup, no other
config change):

- `!define INSTALL_MARKER ".pi-desktop-install-marker"`.
- `customInit`: if `$INSTDIR` exists, is non-empty, and has NO marker →
  MessageBox(stop) + `Abort` — dangerous `/D=` into an existing foreign
  directory is rejected before extraction. Empty/new dirs stay allowed;
  upgrades of our own installs (marker present) stay allowed.
- `customInstall`: write the marker (`APP_ID` + `VERSION`) after extraction.
- `customUnInstall`: if the marker is missing → `Quit` before any
  deletion — a tampered/broken state never triggers recursive deletion.

Contract tests pin the include name and a content allow-list; the CI
lifecycle gains three RED→GREEN scenarios (malicious /D=, tampered
uninstall, failed-install leaves prior install intact).
